The behaviors that make it "agentic"

⏱ 31-Second Adaptation

On a failed login or failed exploit, the LLM diagnoses the failure, rewrites the authentication code, and redeploys — roughly 31 seconds per iteration.

🧬 Self-Modification

When detected or blocked, the payload polymorphs. This is code that reasons about its own signature and changes it.

🏆 Credential Priority Ranking

Harvested secrets are ranked by the LLM for exploit potential — AWS keys outrank local passwords automatically.

🕸 Autonomous Pivoting

Given a foothold, the agent explores lateral-movement options on its own instead of waiting for a human.

🔑 No-Key Encryption

After encrypting, the key is exfiltrated to C2 and never stored on disk — recovery without the key is impossible.

🎭 Masquerading

Persistence units are named like benign services — cloud-sync, update-daemon — to blend with the environment.

THE 31-SECOND ADAPTATION LOOP — failure → diagnose → rewrite → redeploy

Command & Control

C2 infrastructure — build, rotate, burn

The C2 environment guide treats infrastructure as the "nervous system" of the operation: disposable, rotating, layered, mimetic, encrypted. Five principles govern every node.

🌐 HTTPS C2 — the "CDN"

An nginx server with a valid Let's Encrypt cert that mimics a CDN analytics endpoint: returns 404 for GETs, silently accepts encrypted POSTs, with /health and /static/ endpoints that look legitimate. No server-side logging.

[CLIENT] --HTTPS POST (Fernet, chunked)--> [NGINX :443 CDN-mimic] --> [handler.py :8080] --> /opt/c2/incoming
              X-Chunk-ID / X-Chunk-Seq headers

🔐 Client exfil flow

The exfil.py client encrypts with Fernet (AES-128-CBC + HMAC), chunks to 1 MB, POSTs each chunk with a browser-like User-Agent, retries twice per chunk — then overwrites the source with random bytes and deletes it.

  • Fernet key generated fresh per operation
  • Chunk reassembly by ID + sequence order
  • Source shredded with os.urandom overwrite

📡 DNS tunneling

Data rides in DNS queries — the most permission-less channel on any network. Three methods: dnscat2 (full interactive tunnel), Python stdlib exfil (encrypt → base32 → 40-char chunks → gethostbyname with 1–5s jitter), and iodine (IP-over-DNS full tunnel).

🧩 Why DNS wins

  • Works even where egress is locked to 53/UDP
  • Queries look like normal resolution traffic
  • Paper-thin footprint — stdlib only, no binary
  • Server side: dnscat2 with --security=open
KEY CONSTRAINT: DNS payloads are capped (~255 bytes/query) — it's the stealthiest channel, not the fastest. The playbook pairs it with SEN-0 credentials.

📦 ICMP tunneling

Data hidden in ping payloads via icmptx — or manual raw-socket ICMP echo requests (low-and-slow, one 1400-byte chunk per second).

🧷 HTTP headers & WebSocket

Data embedded in custom HTTP headers (X-Tracking-ID) to a beacon.gif — looks like CDN tracking. WebSocket channels run full-duplex over wss://, blending with real-time web apps.

☁️ Cloud as dead-drop

S3/GCS/Azure buckets configured public-write, private-read. Targets upload encrypted data via aws s3 cp or anonymous curl PUT; operator syncs it down. Legitimate cloud traffic is nearly un-blockable.

⚡ Lambda C2

An AWS Lambda "logging endpoint" decodes base64 log payloads and stores them as innocuous analytics/<request-id>.log keys in S3 — a serverless C2 with no server to burn.

🔗 3-hop chain

Operator → Entry (Tor → VPS-1 via SSH, burned every 24h) → Relay (VPS-2 reverse tunnel, rotated per op) → Exfil (VPS-3 clean cloud with valid cert). Each hop uses a different provider, payment method, and jurisdiction. Proxychains stacks Tor + two SOCKS hops.

Traffic path:  Tor --> VPS-1 --> VPS-2 --> VPS-3

Engineering detail worth noticing

The kits aren't just prose — they're tested. The README documents playbook fixes applied in the real kit (firewall order for certbot --standalone, stopping nginx before cert issuance), and each kit ships a local smoke test that proves the full channel on localhost before any VPS is touched.

HTTPS kit smoke test: generate random file → start handler → run exfil.py --plain → run pull.py → sha256-compare recovered bytes to source. Exit 0 = the whole channel is sound.

🛡 OpSec checklist (from the playbook)

  • No server-side logging (access_log off)
  • No bash history on any box
  • Valid TLS certs only — never self-signed
  • Legitimate User-Agents, rate-limited, jittered
  • Ephemeral infra, minimum 2-hop chains
  • Fresh keys per operation, never reused

🔥 Mistakes that burn operators

  • Reusing domains across ops → cross-op attribution
  • Self-signed certs → instant red flag
  • Consistent User-Agent → fingerprinting
  • No rate limiting → anomaly detection triggers
  • Plaintext in transit → DLP captures it
  • Single-hop C2 → one subpoena from the operator
Read Before Use

What this kit is — and isn't

This is a red-team / adversary-emulation framework for authorized engagements only. The README's own safety checklist requires: ownership or written authorization of every target, no attribution trail back to the operator, fresh per-operation keys stored offline, a rehearsed burn procedure, and legal counsel review of the engagement plan. Unauthorized use of these scripts is illegal.

✔ What it is

  • A prompt kit that makes an AI assistant produce structured tactical output
  • A threat model of a hypothetical LLM-driven ransomware ("ATA")
  • Lab tooling to emulate that adversary against your own systems
  • An educational artifact on how agentic threats reason

✖ What it isn't

  • Not a verified threat-intel report on real-world malware (JADEPUFFER is a profile for emulation, "first observed July 2026" per the docs)
  • Not a weaponized, turnkey attack kit — deployment is manual and auth-gated
  • Not a product you can point at a target without authorization
The framework's own conclusion: "The only way to understand the weapon is to wield it — in the lab." The kit is built around that lab boundary.
